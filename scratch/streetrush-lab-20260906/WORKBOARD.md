# StreetRush：四种工作方式，第一批实际产物

2026-09-06。这里的分类按工作方式，而不是传统开发阶段。文章与方案由主代理亲自阅读、判断；子代理只做有边界的源码检索、工具检查与验证。

## 1. 先形成完整方案：赛道空间与环境

- 产物：`ENVIRONMENT_PLAN.md`，给出维修区模块、布局、资源用法、取舍和生产接入边界。
- 本批状态：方案已写；独立样片中的直道/维修区用于验证一部分空间关系，不等于已经改造完整赛道。
- 下一项必须解决：将样片认可的模块落到生产中心线的具体弧长区间，核对护栏、路肩和碰撞范围；不能直接复制样片坐标。

## 2. 多版直接试：UI 与相机

- 产物：`index.html` 的三套 UI（俱乐部、工程、极简）和三套追车参数（现有构图参数、低位跟随、稳定前视）。
- 本批状态：独立页面实现，真实三维场景中切换；不是三张静态效果图。
- 体验边界：同一固定轨迹适合比较车在画面中的大小、视距与镜头跟随；未连接生产物理，不能拿它验收转向、制动或真实驾驶手感。轮组没有在该轨迹演示中完成动态绑定。
- 下一项必须解决：选择有价值的视觉差异后在生产真实驾驶中复核，尤其弯道、倒车、碰撞和低帧率。

## 3. 新能力实验，优先推进：可调的三维维修区

- 产物：`lab.js` 程序化构造五跨开放维修棚、控制室、遮阳棚、看台长凳、路灯、护栏、制动牌、草簇与树群；加载已有 MX-5 和已下载的沥青/草地通道；加入天空、光照和实时阴影。
- 可控方式：固定随机种子；结构尺寸在源码中明确；UI 可调太阳高度、曝光、材质、投影和细节；可保存当前参数 JSON。
- 本批状态：可运行的能力样片第一版。建筑与植被仍是程序化原型质量，未达到最终美术资产标准；没有使用 Blender，也没有把这个结果描述为摄影级成品。
- 下一项必须解决：建筑表面与接缝、植被轮廓、复杂车模阴影成本，以及参数配方的一键重新导入。目前 JSON 保存用于记录，未实现导入按钮。

## 4. 复杂集成工程：车辆求解与宿主边界

主代理负责整体合同、算法选择和最终结论；有限子任务输出证据或补丁建议；按当前项目规则，生产编辑仍由主代理完成。以下已根据源码定位，不是已实现的修复。

| 子任务 | 已定位入口 | 输出 | 依赖与限制 |
|---|---|---|---|
| 冻结候选输入 | `vehicle-v24/runtime.js` 的 `step:141–269` | 输入/接触包与 canonical 写入清单 | 不能把重命名现有阶段当作全局求解完成 |
| 残差与 active set | `runtime.js:271–440` | 各残差来源、单位与耦合关系 | 当前 max 聚合不等于同一全局 candidate 的残差 |
| 接触/Delassus | `rapier-host-adapter.js:102–245` | 法线/切向基、地面速度、有效质量的契约与对照 | 保留现有 authority 与 accepted 语义 |
| 提交与异常 | `runtime.js:440–484,613–641` | exactly-once 与失败阶段矩阵 | 与 FiveOwner transaction 和宿主共同裁定 |
| 世界力与回滚 | `rapier-host-adapter.js:247–311` | writer 账本及回滚覆盖范围 | 不能清除其他 writer 的贡献后称精确回滚 |

本批状态：工作边界定位完成，未修改或执行新的物理验收。复杂包不能阻挡独立的 UI、环境和素材实验；也不能靠表现效果掩盖尚未闭合的物理实现。
