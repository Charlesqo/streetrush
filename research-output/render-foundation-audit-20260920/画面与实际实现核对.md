# StreetRush：画面与实际实现双向核对

2026-09-20。本轮只核查；生产源文件、资产、材质和光照参数未修改。

## 核查口径

不能先把注释、变量名、文件名当成已实现的能力，再为它选择优化方案。本轮同时检查正常游戏画面与实际执行路径，区分：**真实执行了什么、它的边界是什么、当前画面暴露什么、改动会牵连什么**。

在独立 5174 端口注入只读观察器，走正常 `main.js`，没有开启 `renderreview`，没有覆盖相机、光照、材质和自适应画质。保存 MX-5、E30、911 的菜单画面，以及 MX-5、911 的静止驾驶画面；每张 PNG 有同名状态 JSON。没有做全赛道运动验收或性能结论。

当前 CSS 762×652，正常绘制 1028×880，比例 1.35。此前车辆诊断使用 1524×1304、固定近景与开发模式，其结论不能直接当作正常驾驶效果或性能的验收。

![正常入口的 911 静止驾驶画面](normal-911-race.png)

整幅画面的直观问题包括：车与路边环境的质感不一致，大片路面和远景的层次有限，车底暗部聚集，正常追车构图中车辆占比较小。它们是视觉观察，不能仅凭截图为每项指定唯一原因。以下用真实实现约束解释。

## 1. “受光统一”目前没有覆盖整幅画面的对象

**真实执行：** 运行时有 348 个远景树实例，使用 `MeshBasicMaterial` 和两张图片；不投太阳阴影。树对象的 `receiveShadow` 标志却是 true。检查实际 MeshBasic 着色器，没有太阳灯光或阴影贴图计算。树的图像额外乘以约 2.8 的颜色系数，并被自定义 shader 提亮。车、路面和大部分建筑使用受灯光影响的 Standard/Physical 材质。

**画面联系：** 树的明暗很大程度保留在图片里，不能自动跟随当前太阳塑形。它与受光的地形、围墙采用不同的明暗来源。这提供了场景拼装感的一项实际依据，但不是整体观感差距的单一解释。

**改动牵连：** 改太阳强度会改变车和地形，树不会以相同方式响应；改最终曝光又会同时改变它们。因此不能靠一个全局亮度参数修好所有对象。

**边界：** 远景图片树本身是一种可用简化；当前核查证明的是它的行为边界，以及字段不等于实际能力。不能据此宣称必须换成昂贵几何树。

依据：`src/track-detail-materials.js:createTreeMaterial`、`src/track-environment.js`、`node_modules/three/src/renderers/shaders/ShaderLib/meshbasic.glsl.js`、逐帧 JSON 的 `meshes` 与 `materials`。

## 2. 所谓“环境反射”同时承担多种受光职责

**真实执行：** `captureVenue` 在固定 `(-55,2.5,12)` 捕获一次场景，隐藏车辆、关闭投影并去掉雾。起点在约 `(-320,0,0)`。三个车型的实际记录使用同一张环境图，强度 0.8；另有强度 0.48 的半球补光和 3.5 的太阳。运行路径没有随车位置更新反射的调用。

Three 的 Standard/Physical shader 把这张图同时用于间接漫反射、镜面反射和清漆反射。它不是只负责车漆上的倒影。全场统一输入也没有描述各个座舱、轮拱、建筑遮挡位置所见的不同环境；本轮可见场景材料没有 lightMap。

**画面联系：** 车身能够反射天空和场地，但附近物体与车身之间的联系近似且固定。暗处的环境补光并不等价于按真实空间遮挡计算的光。仅凭“有环境图”不能把这些能力视为已经建立。

**改动牵连：** 提高环境强度可能同时提亮车漆、轮胎和内饰；提高图像精度不能产生缺失的空间遮挡。捕获的建筑表面还依赖捕获时的太阳、补光和既有环境输入，改捕获策略需要一起检查这些依赖。

**边界：** 尚未定量分离这些近似对最终观感的贡献；不把它直接改写成“必须上某种 GI/反射算法”。

依据：`src/rendering.js:captureVenue/setPreset/update`、`src/main.js` 启动与逐帧调用、Three 的 `lights_fragment_maps` / `envmap_physical_pars_fragment`、逐帧环境 UUID。

## 3. “材质规范化”目前主要是按名称猜测并覆盖常量

**真实执行：** 加载后调整尺度和朝向，调用 `refineCarMaterials`，绑定有显式清单的轮组，再按材质合批。材质职责来自少量车型映射和正则匹配，不是覆盖所有部件的显式资产定义。

911 的实例说明这种缺口：opaque 的 blackGlass 被染成统一蓝灰；轮胎 `Scene_-_Root.002` 没匹配 rubber，保留约 0.43 金属度；carbon 被分到 plastic，实际仍是 Standard，代码中的 Physical 清漆赋值没有执行。一个源玻璃材质还被车窗、灯罩、仪表共用。

**画面联系：** “塑料感”可能包含错误部件职责、信息缺失和公共受光近似。即使 shader 本身真实执行，输入也不能仅凭名字认为正确。

**改动牵连：** 调整一个共享材质可能同时改变车窗和灯罩；合批后已经丢失部分单独部件边界。若要定义部件职责，必须先核对源节点用途与共享关系，再决定在哪一阶段分离，不能无条件增加运行时特判。

**可复用部分：** 轮组已有独立显式清单，导入、几何合批和材质复制也有实现。它们仅证明各自职责，不能替表面材质的完整定义背书。

依据：`src/assets.js:normalizeCar/mergeStaticCarMeshes`、`src/car-materials.js`、现有 GLB 审计与本轮正常入口的 911 材质状态。

## 4. “玻璃”和“接触遮蔽”是多种近似叠加，职责需要看清

**玻璃实际执行：** 保留源 alpha，透明混合、通常不写深度、不投影，`transmission=0`。它仍有表面高光，但没有在这条路径中实现厚度吸收和折射。当前记录中没有 transmission 大于零的材料。

**遮蔽实际执行：** 太阳投影、车辆下方固定软圆片、材质 AO 图和 GTAO 各有职责。车辆“contact-shadow”实际是一张挂在车模型下的渐变透明圆片，不会根据车底几何实时生成接触阴影。GTAO 使用主场景深度重建法线，再用乘法混合压暗已着色的整张场景色。

**画面联系：** 轮拱/座舱的深度感、玻璃前后的层次，不是靠同一个可靠的空间遮挡模型给出的。透明表面通常没有进入深度，屏幕遮蔽看到的是它后面的不透明几何。

**改动牵连：** 加重 GTAO 会连同直射光和反射一起压暗，不是只减少间接光；把玻璃改成写深度会影响 GTAO、透明排序和其它读取场景深度的效果；加入透射路径又会改变渲染次数和合成条件。不能只看玻璃特写就认为修改通过。

依据：`src/car-materials.js`、`src/assets.js` 的 contactShadow、`src/render-pipeline.js`、Three 的 `GTAOPass` 与 `GTAOBlendShader`；运行时记录的传输值、深度和 blend 状态。

## 5. “项目里有 Megascans”不等于当前画面用了那套内容

**真实执行：** 正常入口使用 `dry-asphalt`，实际贴图来自 `/textures/asphalt/asphalt_01_*_1k.jpg`。场地另有自己的材质。三个车型快照均没有名为 Megascans 的材料。

`installStraightArt` 的扫描主直道替换只在开发入口同时满足 `circuitreview/pitpreview` 与 `straightart` 时加载。它的多通道采样、材质替换和反射响应实验不能当作正常入口的现有能力。这个判断同时来自入口条件和实际材料清单，不只来自文件名搜索。

**画面联系：** 不能用预览工程的内容解释正常游戏的路面，也不能因目录里出现高质量素材而判断整套输入已有基础。

**改动牵连：** 正式接入该预览会改变几何分组、道路及路肩材质，还有独立 shader 处理，需重新检查和其它场地材质、阴影、反射、预算的关系。

依据：`src/main.js` 的 `straightart` 条件、`src/dev-straight-art.js`、正常入口材料的贴图 URL。

## 6. 有实际执行的输出基础，但尚不能代替质量结论

**本机记录的真实每帧顺序：**

1. 场景色与深度，1028×880、HalfFloat、4× MSAA。
2. GTAO 与去噪，各 514×440；法线从深度重建，没有独立材质法线缓冲。
3. 将场景色复制到合成目标，并乘上遮蔽结果。
4. 有烟时额外合成烟，本轮静态帧无烟。
5. OutputPass 输出屏幕，实际启用了 ACES 和 sRGB 转换。

检查 Three 对非屏幕目标的处理，这条已观察主链没有重复做 ACES/sRGB 的直接证据。不能看到“发灰”就先认定颜色空间坏了，也不能据此认定颜色与曝光已经校准。

**改动牵连：** 正常运行会自适应降低 AO 分辨率，再降低主分辨率；此前 2×、固定近景的诊断跳过了这套控制。MSAA 真实启用并不证明碳纤维、格栅和高光在运动中稳定。本轮没有验证运动稳定性和目标设备帧时间。

依据：逐帧 `passes`、`renderer`、`ao`，`src/main.js:updatePerformance`，`src/render-pipeline.js`，Three 的 `WebGLRenderer/OutputPass`。

## 当前判断与后续工作边界

当前已经发现**明确的职责缺口和不同近似之间的连接问题**。这些足以否定“已有一个完整可靠基础，只需调漂亮”的工作前提；也不支持直接把所有模块推倒或列一个高级技术采购清单。

后续每个候选改动需要同时给出：

- 它针对完整画面的哪种缺陷，现有实现的哪条证据支持这个判断。
- 它实际改变哪个输入、计算或合成环节，以及会影响的其它对象/车型/显示状态。
- 在相同正常入口条件下，完整画面是否改善、原问题是否改善、相邻职责是否退化。
- 仍未知的部分，不把单机位改善写成全系统成立。

目前不宣称已定位所有质量瓶颈、已决定重建架构或已建立高质量样板。下一步应优先把上述受光、反射、遮挡、透明和材质分配的实际职责与输入边界理清，再针对完整画面选择可撤销的实验；不是再按技术名称补功能。
