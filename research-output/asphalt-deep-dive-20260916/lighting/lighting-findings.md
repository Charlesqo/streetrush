# 当前游戏实际 HDR、太阳与环境捕获核查

2026-09-16。仅读取源码与原始 HDR；未执行附件原型，未修改游戏源码，未运行 GPU 实验。

## 结论先行

1. 当前太阳方向确实与这张 HDR 最亮像素对齐；没有发现“天空太阳和解析太阳明显错位”的证据。
2. `min(radiance,8)` 在这张实际 HDR 中主要切除太阳及近太阳高亮，不是大片天空云层。切掉的天空能量很大，但解析太阳把多数补回来了。不能只报“天空损失 61%”就认定整场缺光。
3. 在受控、未遮挡、天空原图数值尺度一致的 CPU 参照里，解析太阳 3.5 补回被移除方向照明约 86.5% 的亮度能量；再计入半球补光，朝上漫反射入射量接近完整 HDR 参照。粗糙镜面则没有半球补光补偿，且另有 DFG/PMREM 近似，因此亮度够了仍可能显得平、颗粒反光不充分。
4. 比单独改 clamp 或太阳强度更值得优先实测的是：**直接镜面 / 环境镜面 / 两种漫反射分项，真实 normal/roughness，固定探针历史的对照**。尚不能从 CPU 天空积分宣布当前实际画面各项损失多少。

## 1. 当前运行链，而非初始化默认值

- `src/main.js:1411` 调用 `lighting.setSkyRotation(-1.1, vehicle?.visual)`，进入 HDRI preset。
- `src/rendering.js`：HDR 背景 gain=1；场景环境强度 `.8`；解析太阳 `0xffeed6 × 3.5`；半球补光 `.48`；曝光 `.9`；ACES 输出；雾密度 `.00038`。
- HDRI 是 `public/textures/sky/kloofendal_48d_partly_cloudy_puresky_2k.hdr`，2048×1024，5,451,493 bytes，SHA-256 `5244534e9cf5b606f2ff513aa00ddb161b0a4826ffd88a0d3bd03ac29247d198`。
- 显示背景不执行 clamp8；捕获环境时 `captureMode=1`，先逐 RGB 通道 clamp8，再进入 PMREM。
- 捕获位置固定 `(-55,2.5,12)`，单个 256 面尺寸探针；预模糊 sigma=.025 rad；随后生成 PMREM。
- 捕获时隐藏车辆、关阴影、清除雾，但保留场景物体当前材质和上一次 `scene.environment`。
- 本地 r180 `PMREMGenerator._sceneToCubeUV` 明确暂时设置 `NoToneMapping`；不能把捕获误说成已经 ACES 压缩过。

来源定位：`src/rendering.js:77–124,156–180`，`node_modules/three/src/extras/PMREMGenerator.js:339–456`。

## 2. 如何核算原 HDR

本目录 `audit_hdr.py` 独立解码 RGBE，不导入附件代码；使用与 r180 一致的 RGBE/255 和 HalfFloat 截断规则。`verify_hdr_loader.mjs` 再使用项目官方 HDRLoader 解析，整张 RGBA half 数据逐字节 SHA 相等：

`b331a46f5fb989529b72ea0f4f825bb7841af6420fa679dbd9b37213941e781e`

采用原图每个 texel 中心的方向和经纬网格精确立体角权重，积分结果使用线性 RGB；亮度标量为 `.2126 R + .7152 G + .0722 B`。未将原图数值当成标定过的 cd/m² 或 lux。未模拟 GPU 双线性采样、256 cubemap 重采样、遮挡、场景反射、PMREM 或 tone mapping。

原始 HDR 两个像素超过 float16 最大值 65504。默认 HDRLoader 会压到 65504，再做 half 精度转换；整个球面加权亮度积分损失约 1.04%。下述 raw 均指已匹配实际加载器的运行时 HDR，不是偷偷保留 GPU 没有的超限峰值。

## 3. 太阳方向是对的

独立找到最高亮度 texel `(1218,239)`，与源码采用的像素中心 `(1218.5,239.5)` 一致。按实际旋转 -1.1：

- 太阳仰角 **47.9004°**。
- 世界方位角 **-28.8359°**（+X 为零，向 +Z 为正）。
- 从表面指向光源的单位方向 **[0.587292, 0.741980, -0.323346]**。
- 半球补光不产生直接镜面高光，不能把它当作另一盏太阳。

诊断装配的一个实际陷阱：`setSkyRotation(value, visual)` 内部通过 `update(visual,...)` 才把方向写回 DirectionalLight 的 position/target；`update` 遇到空 visual 会提前返回。正常 main 有 vehicle.visual；独立实验若传 null，会出现“天空方向已经更新、解析太阳还留在初始化方向”的错误。必须提供固定 Object3D，并检查真正的 light.position - light.target.position，而不能只打印 lighting.direction。

对理想水平路面，方向光的完美镜面方向也是约 47.9° 高于路面。1.7m 相机看到的理想平面太阳镜像在约 1.54m 的水平距离、沿背太阳方位；这与看十几米外路面的驾驶掠射角不同。较远处的骨料反光依赖局部法线 / 微面分布，而非只要“有太阳”就应该整条路都密集闪。真实粗糙路面的宽反射瓣仍能在其他方向响应。

## 4. clamp8 实际切了什么

| 指标 | 当前 HDR 的结果 |
|---|---:|
| 受到任一通道 clamp8 影响的上半球立体角 | **0.23694%** |
| 受影响像素离太阳中心的最远角距离 | **6.98°** |
| 被移除能量的 50% 所在半径 | 0.2115° |
| 被移除能量的 90% 所在半径 | 0.3535° |
| 被移除能量的 95% 所在半径 | **0.4994°** |
| 被移除能量的 99% 所在半径 | 2.6395° |
| 上半球 ∫L dω，raw → clamp8 | 7.21943 → 2.80749（-61.11%） |
| 水平路面 ∫L cosθ dω，raw → clamp8 | 4.73970 → 1.46734（-69.04%） |

约 78.5% 被移除能量在太阳中心 .27° 内，95.1% 在 .5° 内。存在切掉近太阳辉光 / 高亮区域的尾部，但这张图不存在“clamp8 把远离太阳的大量普通云块一起抹掉”的证据。完整角度分箱见 `clipping-angular-bins.csv`。

这些大比例是**去掉太阳、还没加解析太阳的天空分支**，不能与最终屏幕亮度画等号。

## 5. 太阳 3.5 与被切掉的 HDR 是否相称

方向光 `0xffeed6 × 3.5` 经过 sRGB→linear，线性 RGB 为 `[3.5,2.99247,2.35355]`，亮度标量 3.05424。

将被移除的天空按当前环境强度 .8 缩放，对准太阳方向的平面所损失的线性入射 RGB 为约 `[3.55314,3.54954,3.26024]`。解析太阳与其比值约：

- R：98.50%；G：84.31%；B：72.19%；亮度：**86.54%**。

因此它在当前 HDR 的渲染数值尺度中是接近量级、稍弱且更暖的替代，并非完全没补。没有物理曝光 / 辐射标定，所以不能说该参数就是现实中的多少 lux。

| 面朝向 | 完整 HDR × .8 | clamp8 HDR × .8 + 解析太阳 | 解释 |
|---|---:|---:|---|
| 朝上水平路面 | 3.79176 | 3.44006 | 比完整 HDR 低约 9.28% |
| 正对太阳的平面 | 5.03827 | 4.56310 | 比完整 HDR 低约 9.43% |
| 背太阳的 -X 竖面 | 0.54210 | 0.54210 | 本参照中被裁掉方向原本不照此面 |

朝上半球补光入射亮度另为 **0.37207**。于是朝上 `clamp8 天空×.8 + 解析太阳 + 半球补光` 的理想入射量约 **3.81214**，已接近完整 HDR×.8 的 **3.79176**。这只是天空无遮挡 / 单次反射参照，未包含真实探针和材质；但它足以推翻“只看 clamp 前后百分比就断定场景大幅缺光”的论证。

半球补光主要补了漫反射，不补同等镜面方向信息，可能提高平亮底色而没有恢复颗粒对比。这是应当用分项图核验的具体方向。

## 6. 多朝向粗糙镜面参照

独立对这张原 HDR 积分 r180 直接光 GGX（correlated Smith、指数 Fresnel、F0=.04、roughness=.837、平法线）。比较 `完整天空 × .8` 与 `clamp8 天空 × .8 + 当前解析太阳`。这里没有使用 DFG / PMREM，故可把“光源分拆造成的变化”和“引擎环境近似”分开。

NdotV=.1，约等于 1.7m 高相机看 16.9m 外水平地面。V 为**从路面指向相机**的方向，避免与相机看向混淆。

| V 水平朝向 | 完整 HDR 单次镜面 | 分拆天空+太阳 | 后者/前者 |
|---|---:|---:|---:|
| +X | .036516 | .034220 | 93.71% |
| -X（与沿主直道看 +X 的关系更接近） | .096448 | .087912 | 91.15% |
| +Z | .055799 | .051813 | 92.86% |
| -Z | .036991 | .034541 | 93.38% |
| V 与太阳水平相反 | .136516 | .123394 | 90.39% |
| V 与太阳水平相同 | .034391 | .032126 | 93.42% |

这说明当前光源分拆在这些平面受控条件下并没有消除全部粗糙反光，且同一材料随观察方位本来就相差很大。实际游戏环境分支还会受 DFG 和 PMREM 影响；不能把本表当作已经测到了最终游戏的 AOV。

额外 r=.3/.6/1、正上方及完美太阳镜像方向结果保存在 `hdr-analysis.json`。r=.3 的完美太阳镜向只保留约87.5%，与非镜向近乎不受影响不同；光源角宽对更尖锐的反射更重要。DirectionLight 没有这张 HDR 原太阳盘的有限角宽。

## 7. sigma=.025、PMREM 分辨率：能确认与不能确认

本地 r180 使用逐级球面两遍 Gaussian 近似，`EXTRA_LOD_SIGMA=[.125,.215,.35,.446,.526,.582]`。**不要用最新版网站写的 GGX VNDF 预过滤倒推 r180 的实现**；研究必须固定版本。

- 额外 sigma=.025 是 **1.432°** 预模糊，确实会先平滑环境的尖锐方向结构。
- r=.837 的 roughnessToMip 为 **-1.185**，取样落在 sigma=.526 和 .582 的最粗等级之间（对应约30.1°、33.3°）。
- 按 Gaussian 方差相加做量级估计，额外 .025 只增加这两级约 **0.09%–0.11% 的核宽**。所以把它称作“高粗糙沥青不反光的首要原因”依据不足。实际离散 cubemap、串联 blur、峰值变化仍需 GPU 读回。
- 对低 roughness 或镜面车漆，预模糊与有限探针分辨率更可能重要；道路不能借车漆的结论。
- 增加探针尺寸可以改善输入角向离散，但不自动修复 DFG、材质 mip 或缺失的局部遮挡。

## 8. 单探针和历史依赖：源码能确认的问题

### 捕获历史依赖存在，但不是同一 target 自读自写

`captureVenue` 在渲染新探针时仍保留旧 `scene.environment`；场景里的 Standard 材质会读取它。新 target 完成后才替换 scene.environment，因此不是同一个纹理边读边写的未定义行为。

但捕获结果在逻辑上确实包含上一轮环境造成的物体受光：第一轮 HDRI 捕获会读初始化的程序天空环境，随后反复点“原场景 / 新素材”又会读上一次捕获。捕获历史可进入下一轮环境漫反射 / 镜面。理论结构是 `E_next = sky + sceneResponse(direct,hemi,E_previous)`，而非每次同参数必然生成相同探针。

可确认调用链；**不能未经 GPU 同状态重复捕获就报历史漂移幅度**。应固定源环境后再 capture，或明确迭代收敛策略，先在诊断页验证。

### 捕获阴影关闭

`renderer.shadowMap.enabled=false`，因此捕获的建筑 / 地面受光没有当前实时太阳阴影。几何仍挡住视线；两者不能混淆。它可能把本应阴影中的表面记录得更亮，再作为环境回送，改变层次。实际影响取决于探针可见几何和材质，需 GPU A/B。

### 一个位置供整条路使用

场景环境统一来自 `(-55,2.5,12)`，实际每像素环境查询只有法线 / 观察方向，没有沿路位置修正或 box projection。天空远场对此较合理，近建筑、护栏、地面在641m直道上并不具有同样的视角与遮挡。靠近护栏、维修区与开阔路面的环境镜面 / 漫反射不可能自动由这个单探针正确区分。

从单探针直接升级大量探针也不能先当答案；先分离天空远场与近场反射，测位置差异和成本。用户需要的是道路质感，不能以此为由先做全场 GI 重构。

## 9. DFG 新发现如何接到这张真实天空上

先前独立积分已确认：r=.837、F0=.04、NdotV=.1 的常数环境单次参照 .0713323，旧 DFG 单次项 .0246386，相差 -65.46%。这个机制成立。

同轮主任务的独立 GPU 实验已进一步复现此趋势（读取 `../runtime/dfg-gpu.json`）：NdotV=.1 的旧环境镜面约 .025595，新参考表约 .072311，均包含现有多次散射。它不是本子任务执行的 GPU 实验，且只验证恒定白环境；太阳关闭，所以不受上文独立实验空 visual 的太阳装配问题影响。主任务另一份旧32组真实材质分项因该装配问题已撤回，本报告不使用其占比。

但这张实际 HDR 高度不均匀，太阳又被单独移出，剩余天空 / 场地 PMREM 需要方向卷积；直接把常数环境倍数乘到当前画面是错误的。新 DFG 会同时影响已有多次散射和间接漫反射能量分配。应先做常数环境 GPU 核验，再在冻结真实探针下输出分项，区分 DFG 与 PMREM 的责任。

## 10. 建议的最小本地验证顺序

1. 冻结当前真实 HDR、相机、曝光、源环境；同场景重复捕获三次，保存线性探针 / AOV，量化历史依赖。
2. 直接镜面、环境镜面、直接漫反射、环境漫反射、半球补光分别输出；统一缓冲精度，不经 ACES 后再猜参数。
3. 固定原环境做常数色、常数 roughness、平法线；常数环境 DFG 的 GPU 趋势本轮已有结果，不必重复相同试验。接下来核验冻结真实环境中的作用，且检查真正的 DirectionalLight position/target。
4. 恢复真实 Fine 通道，普通采样对比当前随机采样；固定灯光，找出骨料反光在哪一步丢失。
5. 保持完整 HDR 能量的对照，与“太阳局部方向遮罩 + 相称解析太阳”的分拆对照；禁止简单同时打开未移除太阳的 HDR 和完整解析太阳来制造过亮高光。
6. 只有分项表明必要，再评估 PMREM / 探针位置与法线过滤。sigma、8K、曝光、太阳强度不应一起改。
