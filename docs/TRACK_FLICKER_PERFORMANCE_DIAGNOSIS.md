# 远景闪烁与性能诊断 — 2026-09-08

本轮按用户要求先诊断，未修改正式游戏的抗锯齿、光照、模型、车辆物理或画质策略。仅扩展 DEV render-review：可在 5 FPS 下做 GPU 计时和车辆步骤计时，并增加场景提交统计及空计时区间校验。采样结束后已关闭诊断页。

## 1. 白线的首要嫌疑：亚像素覆盖不稳定

源码中边线为 0.12 m 宽的独立几何，高度 0.043 m；路面为 0.015 m。起跑格线为 0.16 m 厚的横向几何，其顶面约 0.044 m。正式场景渲染到离屏半浮点目标，桌面只有 2× MSAA，触摸模式为 0×。WebGLRenderer 的默认画布 antialias 不会替这个离屏场景增加采样；目前没有跨帧历史、运动向量或时间抗锯齿。

按 1280×720、FOV 58°、相机离地 4.8 m 的代表性直道视角计算：

| 距离 | 边线投影宽度 | 横向起跑格线投影厚度 |
| --- | ---: | ---: |
| 50 m | 1.56 px | 0.217 px |
| 100 m | 0.79 px | 0.055 px |
| 200 m | 0.39 px | 0.014 px |

运动改变采样位置时，这样的细线容易在少数采样点之间出现/消失。自适应分辨率最低可到 0.72，使 100 m 处的边线进一步降到约 0.57 px。各向异性纹理过滤不解决独立几何的覆盖问题。

相同代表性视角、同一视线下，边线与路面的深度差在 100 / 200 / 600 m 仍约有 99 / 50 / 17 个 24-bit 深度量化级，因此暂不把普通直道白线的主要原因判为共面 z-fighting。其他视角、局部重叠、阴影闪烁仍需分别验证。这里是投影与代码证据，尚未完成相机运动序列的闪烁量化，更未宣布解决。

复现计算：`node scratch/track-diagnosis-20260908/project-lines.mjs`；输出见同目录 line-projection.json。

## 2. CPU 和 GPU 都有成本，静止场景更偏 GPU

硬件为 Apple M4，1280×720，MX-5；预热 3 秒，再采样约 12 秒。出图限制 5 FPS 以降低测试负载，输入/车辆固定步进保持现有运行方式。5 FPS 是人为上限，不能把这里的 200 ms 帧间隔当作性能结果，也不能据此承诺正常游戏帧率。

| 指标 | 静止主直道 | 短时直道驾驶 |
| --- | ---: | ---: |
| CPU 渲染提交 wall time | 3.881 ms/帧 | 7.914 ms/帧 |
| GPU 整条渲染管线 | 15.691 ms/帧 | 本次分段驾驶未测整体 |
| Vehicle.fixedUpdate wall time | 未执行 | 3.065 ms/步，P95 4.5 ms |
| 绘制三角形（含多次 pass） | 598,888/帧 | 平均 1,063,751/帧 |
| draw calls | 220/帧 | 平均 281/帧 |

驾驶步骤计时覆盖 1,441 步，约等于 120 Hz。3.065×120≈368 ms/秒是这个函数消耗的单线程时间预算，不是整机 CPU 利用率；尚未包括 world.step、afterPhysics、声音和 HUD。渲染提交 wall time 也可能包含驱动等待，不能全部当作纯 JS 算术成本。

分阶段 GPU 查询显示场景、AO、合成/输出都值得继续细分。空查询对照为 0 ms，但分段查询仍可能扰动分块渲染，且合成组含额外特效调用，不能简单相加或据此许诺优化百分比。原始摘要见 scratch/track-diagnosis-20260908/measurement-summary.json。

## 3. 已确认的结构问题与边界

- 当前视角主 pass 提交约 593,289 个三角形，车辆约 51,344。车库砖墙一批 102,582，另一个车库材质批 63,882，看台红座椅一批 51,856。主要负担并不只在车辆模型。
- 全圈防护设施以及跨多个建筑的实例批次没有按空间分块，也没有距离 LOD。批次包围体入镜即整批提交。具体可剔除比例尚未量化，不能把上述三角形全部算成可节省部分。
- 车辆移动时阴影通常重新绘制，静态建筑和设施也参与。反射环境已经做一次捕获并复用；不能把它误说成每帧六面重绘。
- AO 每帧生成、降噪、合成。检查页“环境遮蔽 开/关”只切换 blendIntensity，并未跳过 AO 计算，因此不能用该开关的帧率变化作为 AO 成本 A/B 证据。
- 模糊与降分辨率形成联动：低帧率触发缩小画面，远处细线更难稳定采样。
- 场景派生文件约 51 MiB。文件大小主要对应加载与存储；加载后每帧几何、材质采样、多次绘制和车辆计算才是这里有直接测量证据的持续成本。纹理解压后内存用量未单独测量。
- 整机 16 GiB 内存、约 8,921 MiB swap 已使用；两次一秒间隔观测未发生 swap in/out。不能把整机已有交换区归咎于游戏，也不能排除其他时刻内存压力加重卡顿。

## 4. 下一步实施顺序（尚未实施）

1. 先修细线覆盖：评估把白线融入路面材质，以像素覆盖过滤保持远处连续，减少独立薄几何和绘制次数；用固定相机轨迹比较连续帧，避免只看静态截图。
2. 将设施实例按路段分块，给远处看台/小道具加 LOD；在相同视角、分辨率下测实际减少的提交量和 GPU 时间。
3. 拆分可缓存的静态阴影与动态车辆阴影，检查 AO/合成目标与无效果时的多余 pass。保持已存在的环境反射缓存。
4. 再评估时间抗锯齿/跨帧 AO。历史重投影、遮挡变化、车辆/轮胎运动、镜头切换时的历史清除必须一起处理，否则可能用拖影换稳定。跨帧过滤本身有成本；复用并减少当前帧工作才可能提速。
5. 对 CPU 做函数级剖析，先查分配、复制与宿主查询开销；不通过降低 120 Hz 或替换 accepted 车辆模型冒充优化。

当前结论是“有多项明确优化方向，尚无可承诺的提速百分比”。本轮没有运行新的全套物理性能门或 target 验证，也没有做正式游戏优化变更。
